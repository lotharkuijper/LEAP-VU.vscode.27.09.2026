# Toegang, inschrijving, uitnodigingen en Canvas

Besluiten en werking van LEAP op dit gebied, zoals ze in de oude CLAUDE.md stonden. Geen instructies die altijd gelden, maar naslag: lees dit als je aan dit onderdeel werkt, en werk het bij als een besluit verandert.

## Course access, open registration and invitations

### Course access and open registration (2026-10-20)
- Access to a course = membership (`course_members`) or being its teacher; admins see everything. There is no longer a fallback to "every active, visible course". Server: `userHasCourseAccess` (`server/lib/auth.js`) / `canAccessCourseContent` (`server/courses/courseAvailability.js`); database: `is_course_member` in `course_content_is_public`, `sc_can_read_course` and the courses SELECT policy (migration `20261020100000_course_enrollment_mode`, rollback in `supabase/rollback/`).
- Each course has an access route `courses.enrollment_mode`: `closed`, `canvas`, `open` (default for now) or `canvas_open` (exception; needs `confirmBoth`). Only the admin sets it (`PUT /api/admin/courses/:id/enrollment-mode`, logged in `leap_setting_changes`); teachers only see the label. Code: `server/courses/enrollment.js`, dialog `EnrollmentModeDialog`.
- Open registration (`POST /api/auth/register`) requires choosing at least one open course; the choice waits in `pending_course_enrollments` and becomes membership after the e-mail is confirmed and the user logs in (`/api/me/activate-enrollments`). VU addresses (vu.nl and subdomains) are refused for open registration and self-join: VU students come via Canvas (VUnet-id lists, not built yet).
- Students can add an open course themselves on Kies cursus (`/api/courses/:courseId/join`) and leave it again. Teachers add students to their course and may promote them to teacher (Beheer leden).
- Disposable e-mail domains are refused at open registration (`isDisposableEmail`), max 10 registrations per IP per hour. Token budget for open accounts: see `docs/decisions/privacy-en-data.md`.
- Re-check with `server/__tests__/enrollment.test.js`.

### Inviting students (2026-10-26)
- Beheer → Studenten uitnodigen (`AddUsersTab`, `server/courses/courseInvitations.js`, migration `20261026120000_course_invitations` + rollback): a course teacher or admin enters e-mail addresses. Existing account → enrolled as student at once (never overwrites an existing membership), plus a short mail; active course unchanged. No account → LEAP creates it UNCONFIRMED (`createUser`, no auth mail), enrolls it, sets it as active course and queues a personal invitation ("<teacher> nodigt je uit voor <course>"). Role student, unless added via "Docent toevoegen" (below).
- "Docent toevoegen" (Beheer leden, 2026-10-27) uses the same route with `role: 'teacher'`: new or existing account becomes course teacher, a student of the course is promoted (`status: 'promoted'`, no mail), and the mail names the teacher role (`introTeacher`). Every path that makes someone course teacher calls `promoteCourseTeacherProfile` (`server/courses/teacherProfile.js`; profile `docent`, needed by the project/storage RLS), including the pgPool path of `PUT …/members/:userId` (live uses that path) and a Canvas teacher launch. After creating a course the admin sees next steps: Docent toevoegen, Toegangsroute kiezen, Naar cursusmateriaal.
- Invitations ignore the course access route and the VU-address block (Canvas exceptions, closed courses): the teacher vouches; `invited_by` is stored and named in the mail.
- The mail link is `/invite#t=<id.HMAC>` (key `TURN_SECRET`), valid 30 days from the last mail; only on click does `POST /api/invitations/accept` create a one-time login code (`generateLink` invite/magiclink, the GoTrue link itself would expire after a day). New accounts then choose a password on `/activate`.
- Mails go through a DB queue (`mail_status`), max ~20/min and 80/hour, retried 3 times. Teachers: max 300 invitations per 24 h (admins unlimited). Beheer leden shows pending invitations with resend/revoke. Unaccepted after 30 days: membership, invitation and the account are removed, but only an account that was never used (`isUnusedAccount`) and serves nothing else (`deleteIfOrphaned`, then `forgetUser`).
- Tests: `server/__tests__/courseInvitations.test.js`; end-to-end against the DB: `node --env-file=.env scripts/check-course-invitations.mjs` (API on :3001, test account, cleans up).

Canvas (LTI) launches and e-mail-code login: see `docs/decisions/toegang-en-canvas.md`.

## Canvas (LTI 1.3, 2026-10-23)

Any change here is a security decision (login, roles, account linking): ask the `security-reviewer` agent to look at it.

- A course with access route `canvas`/`canvas_open` gets a **Canvas link** in Cursussen beheren (`CanvasLinkDialog`, for the admin and the course's teachers): `<app>/lti/launch?course=<id>`. The teacher adds it in Canvas as an External tool module item (new tab). Code: `server/lti/lti.js` (routes wired in `server/lti/routes.js`), migration `20261023100000_canvas_lti` (+ rollback), instructions for the VU Canvas admins: `docs/canvas/canvas-koppeling.md`.
- Launch: `/lti/login` (OIDC start; state + nonce in process memory, single use; state cookie `SameSite=None; Secure; Partitioned`, Secure also on localhost so Canvas can post back from another site, Partitioned so it also works in a Canvas iframe) → Canvas → `POST /lti/launch` with a signed id_token, verified with `jose` against the platform JWKS (iss, aud, max age, nonce, deployment, message type). Then `processLaunch`: account by `lti_identities` (issuer + Canvas sub), else by exact e-mail (`likeExact`: `_` and `%` are no wildcards) and only to an account whose confirmed login address is that e-mail, else a new confirmed account; Canvas course roles Instructor/TA → `teacher`, Learner → `student` (only roles in THIS course count, never institution roles), a teacher is never downgraded, and a Canvas teacher also gets the teacher profile; `lti_course_links` records the Canvas course; `last_active_course_id` is set. Login without password: `generateLink('magiclink')` → `/lti/start#token_hash=…` (`LtiStartPage`, `verifyOtp`, fragment removed at once). Errors go to `/lti/start#error=<code>` with a translated message.
- Afterwards students who came via Canvas log in directly with a one-time code by e-mail (`POST /api/auth/email-code`, `EmailCodeLogin` on the login page): only for accounts with an `lti_identities` row, `shouldCreateUser: false`, the same answer whether or not the address exists, max 3 per e-mail per 15 min. The auth e-mail hook (`server/account/authEmailHook.js`) has a `magiclink` text with the code itself (`email.auth.magiclink.*`).
- Settings: the Canvas environments (`{ issuer, clientId, deploymentIds, authUrl, jwksUrl }`) are NOT secret. Since 2026-10-29 the admin sets them in Beheer → Instellingen → Canvas-koppeling (`CanvasPlatformsPanel`, `GET/PUT /api/admin/lti-platforms`, chatbot_prompts row `__lti_platforms__`, logged in `leap_setting_changes`; `createPlatformRegistry` merges them with `LTI_PLATFORMS` from the environment, env wins, effective without restart). For Instructure's Canvas cloud the issuer is `https://canvas.instructure.com` (also for vud.instructure.com) and `canvasEndpoints` fills in the sso.canvaslms.com URLs. A refused launch from an unknown environment or deployment is remembered in process memory (`createUnknownLog`, last 5) and shown in that panel with "Neem over". `LTI_TOOL_PRIVATE_JWK` (`node scripts/lti-keygen.mjs`) stays in Key Vault only; it is not needed for launches (only for NRPS later). Optional `LTI_APP_URL`. With no environment at all the routes refuse politely and the dialog shows "not configured".
- The Canvas link must carry `?course=<id>`: Canvas pre-fills the module item URL with the bare `/lti/launch` from the Developer Key, so the dialog tells the teacher to replace it (`canvasLink.step2`, `urlNote`). A bare launch only works for a Canvas course already linked via `lti_course_links`. Dev: Vite proxies `/lti/(login|launch|jwks|config.json)` to the API. Tests: `server/__tests__/lti.test.js` (real signatures, forged/expired/replayed messages).

### Canvas group assignments for projects (2026-10-27)
- The project link is `/lti/launch?course=<c>&project=<p>`, added in Canvas as a GROUP ASSIGNMENT (`assignment_selection` placement). Custom fields `canvas_group_id=$com.instructure.Group.id`, `canvas_group_name=$com.instructure.Group.name` arrive only from a group assignment (otherwise the literal variable name, ignored). `processLaunch` puts a student in the LEAP group with `external_ref = canvas:<issuer>:<groupId>` (created with the Canvas name if needed) and redirects into the room (`next` on `/lti/start`). A student already in an active group stays there (teacher moves win). NRPS read-only scope is requested for a later pre-sync of group membership; not used yet. `server/__tests__/projectGroups.test.js`, `server/__tests__/lti.test.js`. Group modes: see `docs/decisions/projecten.md`.

## Course editions (2026-10-29)
- One LEAP course can serve several cohorts (e.g. a Canvas course per year). "Nieuwe editie" in Cursussen beheren (`CourseEditionDialog`, course teacher or admin; `server/courses/courseEditions.js`, migration `20261029100000_course_editions` + rollback) shows a preview, then: students → `course_alumni` (removed from `course_members`), teachers not ticked → alumni too (the starter always stays), active projects → `archived` with active groups → `finalized`, Studiecafé threads → `archived_at` + locked + unpinned, `lti_course_links.retired_at`. Logged in `course_editions` (summary) and `leap_setting_changes`. Repeating does nothing twice. Nothing of the student's own (journal, explanations, quiz) is touched.
- Alumni are NOT in `course_members`, so they drop out of member lists, groups, announcements and system messages automatically. They keep read/practice access: `is_course_member` and `sc_can_read_course` include `course_alumni`, and so does `userHasCourseMembership` on the server. They cannot form/join project groups (`userIsActiveCourseMember`) or write in the Studiecafé (`isActiveMember`, code `alumni`). Course lists label them "Vorige editie" (`role: 'alumni'`); the projects overview shows archived projects only as a look-back at the student's own finished group (`archived: true`).
- Becoming a member again by any route (Canvas, invitation, self-join, admin) deletes the alumni row (trigger `course_members_clear_alumni`); "Weer actief" in the dialog does it by hand (always as student). A launch from a retired Canvas context never creates or upgrades membership: the user becomes alumnus (`processLaunch`).
- Teacher analytics count from the start of the current edition unless `?edition=all` (`editionStart` in the response).
- Studiecafé: `?archived=1` lists archived threads; students can mute e-mails per course (`studiecafe_course_mutes`, `GET/POST /api/studiecafe/:courseId/mute`, filtered in `enqueueNotifications`). Announcements go to course members only (before 2026-10-29 they wrongly went to every student on the platform).
- Tests: `server/__tests__/courseEditions.test.js`, plus the retired-context case in `lti.test.js`.
